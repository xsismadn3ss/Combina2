# Datos — PostgreSQL (runtime + entrenamiento)

Desde el issue #28 todos los datos viven en **PostgreSQL**. Hay dos bases con
el **mismo esquema** (un único conjunto de migraciones Alembic):

| Base | Variable | Uso | Dónde |
|---|---|---|---|
| runtime | `DATABASE_URL` | feedback de producción | Railway (gestionado) / compose local |
| entrenamiento | `TRAINING_DATABASE_URL` | imágenes, paletas, runs, feedback importado | **solo local** |

En producción **solo se define `DATABASE_URL`**. `TRAINING_DATABASE_URL` no se
define en Railway: los datos de entrenamiento (incluidas imágenes y paletas)
no salen del entorno local. El feedback de producción se exporta a CSV y se
importa a la base de entrenamiento (ver §6).

`backend/training.db` (SQLite) se conserva **sin modificar** en git como
evidencia histórica de los runs y del feedback antiguo, pero está **deprecado**:
ningún módulo de `app/` lo lee ni lo escribe. El único lector SQLite es el
script one-shot `scripts/migrate_sqlite_to_postgres.py` (usa `sqlite3` stdlib y
abre el archivo en modo read-only).

## 1. Capa de datos

- **SQLModel + SQLAlchemy 2 sync + psycopg 3** (`psycopg[binary]`). La API es
  sync y FastAPI la ejecuta en el threadpool; no hay async en la DB.
- Engines cacheados por URL con `pool_pre_ping=True`, `pool_recycle=300`,
  `connect_timeout` y `application_name`
  (`app/db/engine.py`).
- Sesiones: `runtime_session()` / `training_session()` (context managers con
  commit/rollback) y `get_session()` como dependencia FastAPI.
- Repositorios (`app/repositories/`) encapsulan SQLAlchemy; solo los upserts
  idempotentes usan `INSERT ... ON CONFLICT DO NOTHING`.
- `/health` y `/ready` **no dependen de la DB**. `/ready` incluye un campo
  informativo `database:{configured,reachable}` (timeout corto + caché 10 s)
  que no altera el 200/503 de los modelos.

## 2. Esquema

Fuente de verdad: `app/db/models/` + `backend/migrations/versions/0001_initial.py`.
Todas las PK numéricas son `BIGINT GENERATED BY DEFAULT AS IDENTITY`.

### `feedback` (runtime; misma tabla en entrenamiento)

| Columna | Tipo | Notas |
|---|---|---|
| `id` | bigint identity PK | |
| `created_at` | timestamptz NOT NULL | UTC, lo genera el servicio |
| `accepted` | boolean NOT NULL | |
| `score` | double NULL | CHECK `0 <= score <= 1` |
| `palette_type` | text NULL | denormalizado del snapshot |
| `palette_json` | jsonb NOT NULL | snapshot `payload.palette.model_dump()` |
| `image_sha256` | char(64) NULL | CHECK `^[0-9a-f]{64}$` |
| `fingerprint` | char(64) NOT NULL UNIQUE | SHA-256 del contenido |
| `source` | text NOT NULL default `'api'` | `api \| import \| sqlite` |

Índices: `ix_feedback_created_at`, `ix_feedback_accepted`,
`ix_feedback_accepted_created_at`.

`fingerprint = SHA-256(created_at UTC ISO + accepted + score(6 dec) +
palette_json canónico + image_sha256)`. Hace idempotente la importación
(`ON CONFLICT (fingerprint) DO NOTHING`).

**No hay FK a `palettes`**: el feedback es un snapshot autosuficiente y puede
referirse a una paleta generada en producción que no exista en la DB de
entrenamiento (o al revés). Esa independencia también permite importar feedback
entre bases sin crear antes las paletas.

### Entrenamiento

- `images(id, sha256 UNIQUE NOT NULL, width, height, source, created_at)`.
- `extracted_colors(image_id FK ON DELETE CASCADE, rank, hex, l, a, b, weight,
  PK(image_id, rank))`.
- `palettes(id, key char(64) UNIQUE NOT NULL, source, rating, harmony_label,
  created_at)`. `key` es la firma sha256 canónica de
  `source|HEX,HEX,...` (`app.ml.datasets.palette_key`); el UNIQUE reemplaza el
  dedup en memoria y permite `ON CONFLICT (key) DO NOTHING`.
- `palette_colors(palette_id FK ON DELETE CASCADE, position, hex, l, a, b,
  PK(palette_id, position))`. Orden determinista `ORDER BY palette_id, position`.
- `training_runs(id, model, git_sha, params_json jsonb, metrics_json jsonb,
  keras_path, tf_version, keras_version, calibration_json jsonb, created_at)`.
- `feedback` (misma definición que runtime). Se usa para calibrar G y para
  importar el feedback de producción.

## 3. Alembic

```bash
cd backend
# local / CI: crea las bases si faltan y aplica el esquema a las dos
python scripts/db_bootstrap.py --target all --create --upgrade

# una sola base (runtime en pre-deploy de Railway)
alembic upgrade head                    # DATABASE_URL
alembic -x url=... upgrade head         # URL explícita
```

`migrations/env.py` importa todos los modelos, lee la URL de `-x url=` >
`ALEMBIC_DATABASE_URL` > `DATABASE_URL` y toma un **advisory lock** de
PostgreSQL durante el upgrade (varios pods/replicas no migran a la vez).
`upgrade head` es idempotente. **No se usa `create_all`** en producción ni en
tests: ambos aplican las migraciones.

## 4. Docker Compose local

`docker compose up -d postgres` levanta `postgres:17-alpine` con:

- `POSTGRES_PASSWORD` obligatoria (`${POSTGRES_PASSWORD:?...}`).
- volumen persistente `combina2-pgdata`.
- healthcheck `pg_isready`.
- red `combina2`; el servicio `backend` espera `service_healthy`.

## 5. Migración desde SQLite (one-shot)

```bash
cd backend
# dry-run por defecto: no escribe nada
python scripts/migrate_sqlite_to_postgres.py --sqlite training.db --dry-run
python scripts/migrate_sqlite_to_postgres.py --sqlite training.db --apply
```

- Orden: images → extracted_colors → palettes → palette_colors →
  training_runs → feedback.
- Conserva ids de `training_runs` y ajusta las secuencias con `setval`.
- Dedup: `images.sha256`, `palettes.key`, `feedback.fingerprint`,
  `training_runs.id`.
- `params_json`/`metrics_json`/`calibration_json` TEXT → JSONB.
- Reporta leídas/insertadas/omitidas por tabla; es idempotente (re-ejecutarlo
  no duplica datos).

## 6. Feedback de producción → entrenamiento

1. En Railway, el backend escribe el feedback en su Postgres (`DATABASE_URL`).
2. Export protegido (Bearer):

   ```bash
   curl -fsS -H "Authorization: Bearer $FEEDBACK_EXPORT_TOKEN" \
     "https://<backend>/api/v1/feedback/export.csv" -o feedback.csv
   ```

   o `python scripts/export_feedback_csv.py --output feedback.csv`.
3. Import local a la DB de entrenamiento:

   ```bash
   python scripts/import_feedback_csv.py --input feedback.csv --dry-run
   python scripts/import_feedback_csv.py --input feedback.csv --apply
   ```

   `--apply` preserva `created_at`, marca `source='import'` y usa el
   `fingerprint` para no duplicar.

Contrato CSV: encabezados exactos
`id,created_at,accepted,score,palette_type,palette_json,colors_hex,image_sha256`,
UTF-8 sin BOM, `created_at` ISO-8601 UTC con `Z`, `score` con 6 decimales,
colores unidos con `|`, `image_sha256` vacío si no existe o si se pide
`include_sha256=false`. Se prefija `'` a valores que empiezan por `= + - @`
(CSV injection).

## 7. Retención y privacidad

- Retención **indefinida** por defecto.
- **No se guardan imágenes originales** ni rutas de archivo: solo el snapshot
  de la paleta y, opcionalmente, el `sha256` de la imagen.
- No hay PII: el feedback no incluye usuario, IP ni identificadores.
- Purga manual:

  ```bash
  python scripts/purge_feedback.py --before 2025-01-01 --dry-run
  python scripts/purge_feedback.py --before 2025-01-01 --apply
  ```

## 8. Fuentes de entrenamiento (orden de prioridad)

1. **`boltuix/color-pedia` (HF, ~50k, Parquet, MIT)** — arranque inmediato, sin scraping.
   Campos: RGB/HEX + nombre + emoción. Uso: pre-entrenar G y head de compatibilidad.
2. **COLOURLovers API `GET /api/palettes/top`** — top-1000 × 8 `hueOption`
   (red, orange, yellow, green, aqua, blue, violet, fuchsia) ≈ 7k paletas de 5 colores
   con ranking (técnica del paper n-Grams 2023). Uso: G + C.
3. **Sintético del motor HSL actual** — generar (base, armonía) → paleta + ruido Lab;
   etiqueta perfecta día-0 para C y bootstrap de G. Si (1)+(2) no rinden, este es el
   plan B completo.
4. **WikiArt subset** — **descartado en Fase 6 (ADR).** E se entrena por
   destilación de KMeans sobre mosaicos sintéticos + paletas de la DB de
   entrenamiento; el resultado híbrido `HardKMeans` ya cumple ΔE76 < 5 y no
   necesita imágenes de arte.

## 9. Preproceso común (`datasets.py`)

Resize lado mayor 300px · RGBA→RGB sobre blanco · submuestreo 3.000 px ·
RGB→CIELAB (vía `color_spaces.py`) · normalización L∈[0,1], a/b∈[-1,1] aprox.
Dedup por `sha256`. Split 80/10/10 estratificado por `harmony_label`/`source`.
